- A Linux-native Meshtastic gateway on real RF, and a two-node LoRa text. A CH341 USB-SPI radio (`1a86:5512`) under `meshtasticd` (API on localhost only) plus a USB handheld exchanged NodeInfo and two application texts tagged `TRANSPORT_LORA`. Not closed: image publish, Porch e2e, in-cluster USB.
- Survival under congestion demonstrated as the airtime commons, measured: the shared channel has a finite airtime budget, offering traffic beyond it collapses delivery, and admission control (pacing offered load back within the budget) restores it. `demo/resilience/survival.sh` runs one continuous probe across three offered-load phases and `internal/resilience.ReducePhases`/`PhaseReport` (a pure, unit-tested multi-phase reducer, exposed as `nephmeshctl resilience -phases/-labels`) reduces it to a per-phase verdict. Measured (2026-08-10): baseline (1 msg/3s, within budget) 100%, degraded (1 msg/1s, over budget) 50%, adapted (paced back) 90% recovered, so "delivery fell under load and recovered after the adaptation." The airtime model predicts it: at LONG_FAST (~559 ms time-on-air) 1 msg/3s is ~19% channel utilization (under the 25% ceiling) and 1 msg/1s is ~56% (over it), so the measured collapse confirms the model's over-budget verdict is authoritative, exactly as the airtime doctrine already frames it. An honest finding surfaced while building: the recovery lever is admission control, not a modem-preset change; we measured that a faster (lower-time-on-air) preset does not recover delivery in the sim because per-node send rate is capped by a firmware broadcast cadence rather than the PHY airtime, so pacing the offered load is the honest lever here (on real RF a preset change also relocates the channel frequency, a lever this UDP substrate cannot model). The `Reduce` before/after path was refactored to share the crediting logic with `ReducePhases` and stays behavior-identical.
- A hardware-free resilience harness and a first control-plane-independence demonstration, turning the project's load-bearing claim (a management layer, not a runtime dependency: the mesh keeps carrying traffic when the cluster and its site are gone) from asserted into shown with a number. `demo/resilience` stands up a multi-node mesh with no radios (the key finding: a lone `meshtasticd --sim` is a single-node loopback and never meshes, but the Linux build's real UDP-multicast transport carries packets between daemons independent of the API, which is the same data-plane / management-plane separation NephMesh claims in the field), a probe originates sequenced broadcasts and measures per-receiver delivery ratio and latency, and `independence.sh` has the operator's real reconcile loop configure a node, measures delivery, and destroys the management plane mid-run. The reduction is a pure, unit-tested package (`internal/resilience`, exposed as `nephmeshctl resilience`) that splits the probe's event log at the perturbation and reports delivery before versus after. Validated end to end (2026-08-10): the operator applied drift and re-verified a node to `Ready`, and delivery held at 100% both before and after the management plane was destroyed. Honest scope: the mesh is flat and UDP stands in for the LoRa RF link, so this operationalizes the claim on a simulation substrate rather than uncovering a hidden dependency; the two-cluster and real-hardware carrier-outage forms remain. Also surfaced the airtime commons directly: pushing the send rate past the channel's airtime ceiling makes delivery fall at the sender, a measurement the harness is meant to make.
- The spectrum exporter is now wired into in-cluster Prometheus, so the SDR pillar is visible on the same observability plane as the operator instead of an orphan process on a sensor host. A new `packages/spectrum-exporter` kpt package ships a hardened, receive-only Deployment and metrics Service, a `ServiceMonitor` so the Prometheus Operator scrapes the `nephmesh_spectrum_*` gauges, and a report-only `PrometheusRule` (no sensor reporting, stale sweeps, sweep errors, a band sustained-busy) that raises a signal for human review and never actuates a radio. It is simulation-first, like the mesh-gateway node: a new exporter `-replay` flag reads a recorded sweep instead of a radio, so the shipped Deployment publishes the same per-band series with no SDR attached, which proves the whole Prometheus integration in a `kind` cluster at `$0` and lets the package pass the manifest security gate (a live sweep needs host USB access, which the gate rightly forbids in a shipped manifest, so the real-SDR sensor keeps running the exporter directly on the sensor host). `set-namespace` places all resources, including the two `monitoring.coreos.com` custom resources, in the per-clone namespace; the package renders clean under the CI package gate. Documented in `packages/spectrum-exporter/README.md` and the spectrum-validation guide.
- The reader for the out-of-band witness: `internal/meshframe` parses the clear-text Meshtastic packet header (to, from, id, flags, channel hash, hop limit) that travels over the air unencrypted, so a receiver with no channel key can still confirm the sender's node id independently of what the node self-reports. A `nephmeshctl decode` subcommand turns decoded LoRa payloads (hex) into readable packet headers. This is the core of the "the mesh cannot lie about itself" idea: cross-check a radio's self-report against the packets physically on the air. The parser is pure and 100% covered (a synthetic fixture packet reads back as the expected node id). A `hack/install-lora-decode.sh` helper installs the receive-only decode toolchain (GNU Radio, a HackRF source, and gr-lora_sdr) on a sensor host; the over-the-air decode that feeds the parser is validated once that toolchain is installed. Everything here is receive-only.
- An edge AI advisor (`internal/advisor`, `nephmeshctl advise`): a local language model reasons over the sensed spectrum (occupancy plus classified emissions) and the radio config and proposes a mesh action with a rationale, against a local Ollama server so it needs no cloud. It is advisory and report-only by construction: the model proposes, a human (or later the safety kernel of ADR 0002) approves, and the output is guarded, not trusted, so a change to an unapproved preset is downgraded to investigate, an unrecognized action becomes hold, and a bad confidence becomes low. The prompt-building and the response parsing (tolerating code fences and prose, validating the action and preset against the approved set) are unit-tested with a stub model and an httptest Ollama; only the model call is external. Validated on real hardware (2026-08-09) reasoning over a live HackRF Pro sweep: a capable model (qwen2.5:14b) correctly noted occupancy slightly over the ceiling, referenced the classified wideband emission, judged it possibly transient, and held; a tiny edge-resident model (the only one that fits alongside the SDR in shared memory on the sensor host) returned malformed output that the guardrail safely downgraded to hold, proving the safety design on hardware. A `-num-gpu 0` option forces CPU inference so a capable model can run in system RAM on a memory-tight sensor host. See `demo/edge-advisor/`.
- Spectrum classification (`internal/spectrum.Classify`, exposed through the advisor): reads a sweep's time structure (many passes over the same frequencies) rather than one snapshot, so it separates packet-shaped emitters (narrow and intermittent, the shape of LoRa mesh traffic) from continuous or wideband interference (a carrier, or the classic jamming shape), each with a confidence and an explicit unknown. It uses a band-wide noise floor so a zero-variance continuous carrier, which a per-bin floor would miss entirely (a constant signal is its own baseline), is detected. This is the move from "the band is busy" to "busy with what", the prerequisite the closed loop needs to read cause rather than mere occupancy. It is deliberately a signature separation, not a jammer detector, and telling one mesh from another (mine versus a neighbor's) needs frame decode, which stays out of scope. Unit-tested against synthetic packet, continuous, wideband, and idle fixtures.
- A Prometheus spectrum exporter (`cmd/spectrum-exporter`), the exporter the SDR research named as missing: a receive-only service that runs `hackrf_sweep` on a loop, reduces each sweep with `internal/spectrum`, and serves per-band `occupancy_percent`, `peak_db`, `peak_frequency_hz`, and `noise_floor_db` gauges on `/metrics`, putting sensed spectrum on the same observability plane as the operator's node health and giving the Phase 6 closed loop something to read. It publishes aggregates, never a per-bin series, so cardinality stays bounded, and a band the sweep did not cover has its value gauges deleted (bins reads 0) rather than a false zero, the same absent-not-false-zero discipline the node metrics use. The publishing logic (`internal/specexport`) is 100% covered with the Prometheus testutil; the sweep loop is thin. Validated on real hardware (2026-08-09): cross-compiled for arm64, run on the Linux USB host against the HackRF Pro, `curl /metrics` returned live values (915 band ~34% occupancy, peak -39 dB, noise -67 dB; the uncovered 433 and 868 bands correctly reported bins=0 with no occupancy series).
- A `sense_spectrum` MCP tool on `nephmesh-mcp`, so an MCP host can reduce a receive-only SDR sweep to per-band occupancy natively, alongside `plan_intent`. It wraps the same `internal/spectrum` reduction the `nephmeshctl spectrum` subcommand uses, with optional `marginDb` and `noisePercentile`, so both agent surfaces now cover both functions and neither can diverge from the other.
- Receive-only spectrum sensing, the first code of the SDR pillar and the reduction the research sweep identified as the missing glue: turn a raw power sweep into per-band occupancy, not a per-bin series that would explode metric cardinality. A new `internal/spectrum` package parses the rtl_power / hackrf_sweep CSV format and reduces it to per-band numbers (occupancy percent against the band's own noise floor, peak and mean power, and the peak frequency) for a configurable set of bands defaulting to the 433, 868, and 915 MHz ISM ranges. It is pure and hardware-free: it reads a CSV a radio produced and touches no device, so the analysis is unit-tested against synthetic sweeps now and validated against a real capture later with the same code. A `nephmeshctl spectrum` subcommand exposes it (JSON or text), a receive-only capture helper (`hack/spectrum-sweep.sh`, using `hackrf_sweep`, which never keys the transmitter) drives a HackRF when one is attached, and a runbook (`docs/guides/spectrum-validation.md`) walks the validation end to end including the Linux-host policy for USB SDRs. This is sensing (is the band busy, and how busy), not classification (busy with what), which stays later work; the whole path is receive-only and the transmit interlock keeps it that way. Validated end to end on real hardware (2026-08-09): a HackRF Pro on a Linux USB host, receive-only; the parser handled real out-of-order sweep segments and tens of thousands of bins cleanly (including the `-inf` gap markers the new firmware emits, which the non-finite filter drops), the 915 band read a stable ~32 to 34 percent occupancy once integrated, and there was no DC-spike artifact to mask (the Pro eliminates it in hardware). The two pillars were then shown to see each other: with a Meshtastic T-Deck transmitting on its US LongFast channel, the mesh appeared in the sensed spectrum as a 24 dB peak (idle -40.9 dB to -17.1 dB under load) at 906.5 MHz, the LongFast channel frequency, with 1367 strong hits there during the burst versus 0 idle. This also showed that per-band peak power (already surfaced as MaxDB/PeakFreqHz), not aggregate occupancy, is the sensitive signal for detecting a single transmitter. That validation showed a single pass is noisy, so the capture helper now integrates several seconds of sweeps by default (a single pass is opt-in), and the runbook records how to separate real signal from a shaped noise floor with an antenna-off baseline.
- Two agent-facing entry points for operating the mesh, both wrapping the report-only intent compiler so an AI agent (Claude Code, Codex, a local LLM) or a script can plan a mesh with no cluster and no hardware. `nephmeshctl plan` is a shell command: a `CommunicationIntent` in (file or stdin), a stable JSON verdict out (feasibility, selected preset, fleet airtime, and the proposed `MeshtasticNode` specs), or a text summary for a person. `nephmesh-mcp` is a Model Context Protocol server over stdio (newline-delimited JSON-RPC 2.0, hand-rolled so the module gains no dependency) that exposes the same compiler as the `plan_intent` tool, callable natively by an MCP host. Both delegate to a new shared `internal/plan` core so the two surfaces never diverge and both match what the operator's controller computes; the compiler is pure, so this is a true offline dry-run and actuation stays gated behind ADR 0002. The JSON-RPC framing and every method (initialize with version negotiation, the initialized notification, ping, tools/list, tools/call, and the error paths) are unit-tested, and the stdio loop is verified end to end against the built binary; a guide (`docs/guides/agent-interface.md`) shows registration with an MCP host and the tool contract. This turns the intent layer's "declare an outcome, read a verdict" contract into something an agent can lean on today, ahead of the richer live-state MCP layer that remains roadmapped.
- Fleet-wide airtime feasibility in the intent compiler, the airtime-as-a-commons differentiator applied where only the intent layer can apply it. A `CommunicationIntent` may declare `expectedTraffic` (offered messages per node per minute and a representative payload); the compiler then estimates the fleet's share of the shared channel at the selected preset and reports it on a distinct `AirtimeWithinBudget` status condition and `.status.predictedChannelUtilizationPercent`. This is a check the per-node reconcile structurally cannot make: it sees one radio, never the whole channel; the intent layer sees the whole fleet at once. The estimate is deliberately a conservative floor (`airtime.FleetChannelUtilizationPercent`): it counts each originated message once and ignores Meshtastic's flood rebroadcast, so real channel utilization is higher, often several times higher in a dense mesh. The consequence is honest and useful: an over-budget verdict is authoritative (the fleet exceeds the budget for certain even by the floor), while within-budget is necessary but not sufficient, which is why the device's measured `AirtimeHealthy` condition stays the ground truth. Airtime is a separate verdict from renderability: `Feasible` stays about whether the intent compiles, `AirtimeWithinBudget` about whether it fits the commons, and it reads Unknown when no traffic is declared rather than a misleading True. Grounded in a hand-computed reference (verified in the airtime unit tests) and covered by compiler, reconcile, and envtest-admission tests; a larger, rebroadcast-aware model that could hard-gate is left as future work (docs/plans/airtime-budget.md).
- The first slice of the intent layer: a `CommunicationIntent` CRD (`intent.nephmesh.io/v1alpha1`) and a report-only compiler that lowers it to the concrete `MeshtasticNode` specs that would satisfy it, recorded on status, actuating nothing. This is ADR 0001 (`MeshtasticNode` is the compiled output of a higher-level intent, not the source of truth) landed as a deliberately safe first step: the intent states an outcome (a region, a role, an ordered set of approved modem presets, the channels, and the target nodes), and the operator compiles it and reports a `Feasible` verdict, the preset it selected from the approved set (the first entry the airtime model recognizes, so an intent expresses a preference order and a tolerance band at once), and the proposed per-device specs on `.status.proposedNodes`. An empty approved set, no target nodes, or an all-unknown set is reported as infeasible, a verdict on status, not a reconcile error. The compiler (`internal/intent.Compile`) is pure and side-effect-free and reuses the airtime preset table for feasibility so an unknown preset is caught here rather than failing to converge on a device. Report-only is enforced by RBAC, not trusted to the code: the operator's ClusterRole grants no create or write on `MeshtasticNode` from an intent, and the least-privilege golden test asserts that boundary. Autonomous actuation stays gated behind the signed-autonomy and safety-kernel work (ADR 0002). The spec's `nodes` list is keyed by name and `channels` by index (list-map keys), so a duplicate node name (which would render two colliding `MeshtasticNode` specs) or a duplicate channel index is rejected at admission rather than surfaced later; `nodes` is bounded (64) both to keep one intent reviewable and because each target embeds a `Connection` with a CEL rule, keeping the CRD within the apiserver's validation cost budget. Shipped with a `regional-intent.yaml` example, printer columns (Region, Preset, Nodes, Feasible, Age), unit and reconcile tests including a negative assertion that no `MeshtasticNode` is created, and an envtest admission suite that installs the CRD against a real apiserver and proves each hostile intent (empty approved set, no nodes, duplicate name, no transport, illegal region, duplicate channel index) is refused at the door.
- An operations runbook (`docs/guides/operations.md`): install, declare a node, observe it through the printer columns, conditions, Events, and metrics, a troubleshooting section that maps each symptom to the signal (Degraded with the drifted fields, SecretMissing, unreachable, airtime over budget), and day-2 operations (single-node key rotation by updating the Secret, turning a feature off, decommission under Retain, and upgrade). It is honest about what is not built yet (the unpublished image, serial/viaGateway via the operator, Wipe, the fleet rotation and closed loop). This turns the observability work into operator-usable value and addresses the 1.0 documentation gate.
- Example `MeshtasticNode` resources (`examples/`): a basic node and a secure-private-channel node with its Secret, plus a README, so a newcomer has a starting point (there were none). The `MeshtasticNode` printer columns gained Preset and LastHeard, so `kubectl get` shows readiness, region, preset, node id, and last-heard at a glance. And the CI integration test now reconciles an MQTT password to `Ready` against `meshtasticd --sim`, locking the write-only-password convergence fix on real firmware, the exact bug the in-memory fake had hidden.

- A reproducible operator demo (`demo/operator/`), the hardware-free, $0 way for a stranger to watch the flagship work: it stands up a simulated Meshtastic radio (real firmware, no RF) and runs the operator's real reconcile loop to converge it to a declared intent, including a secure private channel, drift detected, only the change applied, reboot, re-verify to `Ready`, the channel confirmed by key-hash match, then proves idempotence on a second run that writes nothing. `reconcile-demo` gained `-channel-name`, `-channel-key`, `-applier`, and `-bin` flags so it can drive and demonstrate the channel path. This is a step toward the 1.0 reproducibility gate and the review's ask to make the value visible rather than asserted; the transcript in the demo README is captured from a real run.
- An airtime-budget prediction (`internal/airtime.PredictedChannelUtilizationPercent`), the "predict" control from the airtime plan and the airtime-as-a-commons differentiator in action per node. When a `MeshtasticNode` declares a modem-preset change, the operator predicts what the channel utilization would become at the new preset (scaling the radio's own measured utilization by the two presets' time-on-air ratio) and surfaces an `AirtimeBudget` status condition, False with the before-and-after numbers when the change is predicted to push the channel past the recommended ceiling. It is deliberately advisory: the declared preset is still applied, because hard refusal of an over-budget change is a fleet decision for a Porch validator (which can see the whole channel), not the per-node reconcile (which cannot see the neighbors). Honest about being a prediction, the measured `AirtimeHealthy` condition stays the ground truth. Unit-tested, hardware-free.

### Added

- A closed-loop proof of concept (`demo/closed-loop/`) that runs the full sense, decide, actuate, verify cycle across real hardware on one bench: the SDR senses the mesh channel's peak power, a threshold policy decides whether to relocate, the operator's reconcile loop applies the new preset, and a second sweep verifies the effect, then restores. A real bench run (2026-08-09) sensed the LONG_FAST channel peak at -17.2 dB, decided to actuate, reconciled to LONG_MODERATE, and confirmed the mesh peak had moved from 906.5 to 903.5 MHz (the bandwidth change relocates the channel slot), then restored LONG_FAST. It is deliberately a proof of concept, not autonomy: one fixed-threshold decision, actuate once, restore, with a restore-on-exit trap so a mid-run failure never leaves the node relocated. Autonomous standing actuation stays gated behind the signed-autonomy and safety-kernel work (ADR 0002); this shows the mechanism works, not the safety envelope that would let it self-drive.
- The operator's actuation and the SDR's sensing were shown to close on real hardware (2026-08-09), the heart of the 0.4 gate. The operator's reconcile loop changed a physical T-Deck's modem preset from LONG_FAST to LONG_MODERATE (applied the drift, waited out the reboot, re-verified to Ready, then restored it), which confirms modem-preset round-trip on a real board (previously proven only against `meshtasticd --sim`). The HackRF Pro, sensing independently, saw the transmission move from ~906.5 to ~902.5 MHz, exactly the shift the 250-to-125 kHz bandwidth change predicts by moving the channel slot, and saw the airtime rise. Three independent measurements of that airtime rise agreed: the operator's own time-on-air model (~559 to ~1642 ms per 40-byte frame), the radio's self-reported channelUtilization telemetry (0.0 to 3.2 percent), and the sensed spectrum (more strong hits per bin). An intent change produced an observable, correctly-attributed RF change, with the node's self-report and an external sensor corroborating each other, which is the redundancy the Phase 6 closed loop will depend on.

### Fixed

- A second, three-lens adversarial review (regressions in the prior round's fixes, the pure analytical core, and the operator actuation path), every finding traced to a concrete input before fixing, with regression tests where testable; the airtime math and the security-critical code (secret redaction, argument construction, meshframe parsing) were reviewed and confirmed clean. In the reducer: `Reduce` applied the healthy-delivery floor to the after-window rather than the baseline, so a dead baseline that then delivered read as "kept delivering" and contradicted `ReducePhases` (the floor is now on the baseline, so the two agree). In spectrum classification: `gridStep` used the global minimum bin gap, so one mis-tiled sub-grid bin collapsed run-grouping and split a wideband jammer into many narrow bins (it uses the median gap now). In the intent compiler: duplicate node names were not rejected on the offline/CLI path (the CRD rejects them via a list-map key), so it rendered colliding specs and inflated the node count and airtime floor (now reported `DuplicateNodeName` infeasible). In the operator: an empty MQTT password Secret silently configured no-auth MQTT (now refused, matching the channel path); `applyAirtimeHealth` substituted 0.0 for an absent metric, an idle-looking value that could mask a saturated node (it now evaluates only reported metrics and shows an absent one as "not reported"); the `ChannelsInSync` and `AirtimeBudget` conditions went stale for a whole outage (now cleared when the device is unreachable); and `Converge` could report `Ready` with a blank node id and blank a good one (the Ready path now requeues on no identity, the apply/reboot flow unchanged). Plus a RadioLib-matching LDRO `>= 16 ms` threshold and a probe `--schedule` negative-value guard. Two findings are documented as tracked gaps needing feature work rather than a one-line fix: day-2 rotation of only the MQTT password on a converged node is not detected (needs a stored password hash), and channel reconcile without the bundled exporter reboot-loops on the stock export format; the occupancy metric's saturated-band limitation is now stated in code.
- An adversarial review fan-out over the resilience harness, the spectrum exporter, and the demo scripts, every finding verified against a concrete input before fixing, caught real defects, fixed with regression tests where testable. In the resilience reducer: `nephmeshctl resilience -phases -o json` always failed because the open phase bounds were the infinity that `encoding/json` rejects (bounds are now nil/null pointers); and a "held up" / "survived" verdict could be asserted over a run that never delivered a message (a zero baseline is not success, so the verdict now requires delivery to actually be healthy). Also hardened: the event parser now takes the `EVENT` marker only as a line prefix, duplicate phase boundaries are rejected as not strictly ascending, and a labels/boundaries mismatch prints a specific hint. In the exporter: the `peak_dbm` and `noise_floor_dbm` gauges were renamed to `peak_db` and `noise_floor_db`, since the values are uncalibrated relative dB, not absolute dBm (the project has no absolute calibration), so the metric name no longer overstates the measurement. In the demo scripts: the delivery probe now writes its event log incrementally instead of buffering to the end, so a slightly slow or killed run is not captured as an empty log and misread as a delivery failure; `independence.sh` takes its perturbation timestamp from the same container clock the probe uses (not the host clock, which can skew under Docker Desktop) and waits for the probe to finish rather than a fixed sleep, and it now verifies the operator actually converged; `up.sh` waits for each node's API before enabling UDP (a blind `--set` against a not-yet-booted node silently left it off the mesh) and clears stale nodes from a prior larger run; `down.sh` now removes the operator container; and the probe validates its `--schedule` and closes interfaces on every path.
- An adversarial review fan-out over the earlier cycle's new code (the intent compiler and airtime, the agent plan/CLI/MCP surfaces, and the spectrum reducer), every finding verified against a concrete input before fixing, caught seven real defects, all fixed with regression tests. In the hand-rolled MCP server: a request id was routed through `any`, so a large-integer id (beyond 2^53) was echoed back corrupted, breaking JSON-RPC correlation (now echoed verbatim as raw JSON); and a nil handler result under `omitempty` could produce a response with neither `result` nor `error`, which is an invalid JSON-RPC success (a success now always carries a result member, null when empty). In the spectrum reducer: `strconv.ParseFloat` accepts `nan`/`inf`, so a single such token poisoned a whole band's noise floor, mean, and occupancy (non-finite bins are now dropped like any other unparseable value), and a stray quote could abort the entire capture and discard already-parsed bins (the CSV reader now tolerates quotes as literal data). In the intent and CLI paths: `expectedTraffic` with a non-positive message rate (reachable offline where CRD admission does not apply) reported a reassuring "within budget, 0%" instead of not-evaluated; multi-document YAML was silently reduced to its first document (now rejected with a clear error, since a plan evaluates one intent at a time); and `plan -h` / `spectrum -h` exited non-zero, treating an explicit help request as an error.
- Made the in-memory test fake faithful to the real device on the axis that hid the two worst bugs of this cycle: it no longer echoes back a written secret (the MQTT password), the way a real device never does. Before, the fake merged and re-emitted everything applied, so a write-only field read as converged in every unit test while reboot-looping against a real device. A new regression test drives a node with a write-only password to convergence through the fake, and a negative control confirms it fails when the drift-comparison exclusion is reverted, so that class of bug can no longer hide in a unit test, not just in the sim.
- Node identity and airtime telemetry are now sourced from the exporter's reliable local-node view (`getMyNodeInfo`) rather than scanned out of the whole `--info` node database, which on a real multi-node mesh could return a neighbor's id or channel load, so the operator would report and act on another node's airtime. As a bonus this drops a device round-trip per reconcile (identity now rides the export the loop already fetches). The fake falls back to `--info`, so unit tests are unaffected; validated against `meshtasticd --sim`.
- Hardening from the security and silent-failure review lenses. The operator's NetworkPolicy egress rule for the Kubernetes API server had no destination selector, so it matched all destinations (0.0.0.0/0) on 443 and 6443, a compromised operator could have exfiltrated the Secrets it reads to any public endpoint on 443; it is now restricted to private (RFC1918) ranges (the in-cluster API server is private). The transmit-interlock gate (`hack/check-transmit.sh`), the wire that enforces receive-only, missed `hackrf_transfer`'s `-c` continuous-wave transmit mode and did not scan Dockerfiles or compiled-language sources; both are now covered. And CRD validation gained bounds that were missing: `ChannelSpec.name` is capped at the device's ~12-byte limit (an over-long name would otherwise truncate on the device, never round-trip, and park the node Degraded), and the serial device path and viaGateway dest now carry the same leading-dash-forbidding pattern the TCP host already had, closing a latent argument-injection surface before those transports ship.
- An adversarial code-review fan-out (five reviewers over the reconcile/device, config, controller/secret, Python helpers, and airtime/metrics, every finding then verified skeptically) caught eight more real defects, all fixed with regression tests. Two were HIGH and both were masked by the in-memory fake: (1) a node with an MQTT password never converged, `BuildDesired` put the password in the compared config but the device never echoes a secret back, so it read as permanent drift and reboot-looped to Degraded; the drift comparison now excludes write-only keys (`config.ForComparison`) while the apply still writes them. (2) The two maximum-range modem presets (LONG_MODERATE, LONG_SLOW) were modeled at coding rate 4/5 instead of the firmware's 4/8, under-counting the airtime of exactly the presets most likely to saturate a channel by about 26%. The rest: the redacting `secret.Value` leaked through non-string fmt verbs (`%d`, `%x`) that bypass `String()`, closed with a `fmt.Formatter`; serial-only "unreachable" phrases (a missing file, access denied) were treated as transient on a TCP transport too, so a fatal helper misconfiguration would requeue forever without surfacing, now gated on serial; an unreachable `--info` between the export and the identity read could flip status to `Ready` with an empty node id, now treated as an unreachable step; a channel-utilization metric was never cleared when the value went unknown; the fake's `ExportConfig` shared its `channels` slice by reference, weakening test isolation; an unparseable channel index defaulted to slot 0 instead of being skipped; and the Python apply helper could half-configure a device on a bad entry (it now validates and bounds-checks every channel before any write), silently mangle a malformed base64 key (now `validate=True`), and mishandle an IPv6 or non-numeric `host:port` (now parsed robustly). Verified against the full Go suite and by re-running the channel path against `meshtasticd --sim`.
- A polish and bug-hunt pass over the recent work surfaced three real defects, all fixed. First, the airtime-budget prediction was effectively dead: the reconcile loop read the radio's telemetry only in the converged branch, but the prediction needs the measured channel utilization while a preset change is still pending (which is precisely when the config is not converged), so it never had inputs; telemetry is now read once up front and surfaced on every reachable step. Second, two status conditions could linger stale: an `AirtimeBudget` False persisting after the preset change converged, and a `ChannelsInSync` report persisting after channels were removed from a spec; both are now cleared when they no longer apply. Third, the operator demo used a 14-byte channel key that real firmware would reject, corrected to a valid length. Each fix has a regression test.
